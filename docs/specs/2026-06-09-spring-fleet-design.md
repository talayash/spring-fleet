# spring-fleet — Design Spec

**Date:** 2026-06-09
**Status:** Approved design, pending implementation plan
**Repo:** `github.com/talayash/spring-fleet` (MIT, open source)
**Local path:** `C:\repositories\spring-fleet`

## Summary

`spring-fleet` is a Claude Code plugin for navigating, tracing, and debugging a
fleet of multi-repo Spring Boot microservices. It targets two pain points:

- **A — Cross-repo understanding:** trace a request/feature across many service
  repos and shared libraries; understand shared-lib change impact.
- **B — Runtime log debugging:** when something breaks in a local dev run,
  correlate logs across services by a trace key, reconstruct the timeline, find
  the failure, and map it back to source.

The plugin is **generic and shareable**; all environment specifics live in a
single, private config file. Generic logic in the plugin → reusable by anyone.
Environment wiring in `spring-fleet.config.json` → private to each user.

## Goals / Non-goals

**Goals**
- One-command adoption (`/fleet-init` scans repos and generates the config).
- Cross-repo call-chain tracing with `file:line` citations (A).
- Trace-key-driven cross-service log correlation + root-cause mapping (B).
- Zero personal/company data in the public repo.
- Cross-platform (Windows PowerShell + bash), Maven **or** Gradle.

**Non-goals (for MVP)**
- Process orchestration / `/run` launch+tee (deferred to a later iteration).
- `/impact` shared-lib consumer analysis (deferred).
- Production/remote log ingestion (local dev only).
- Distributed tracing backends (Zipkin/Jaeger UI) — we read local log files.

## Architecture — the hybrid split

```
spring-fleet (plugin, public, generic)     user machine (config, private)
├── commands/   entry points                spring-fleet.config.json  (.gitignored)
├── skills/     the know-how                  ├─ reposRoot, buildTool
├── agents/     parallel workers             ├─ services[] {name,port,path,contextPath,logFile}
├── scripts/    ps1 + sh, deterministic      ├─ sharedLibs[] {name,path,modules[]}
├── hooks/      optional fleet-awareness     ├─ proxyLib
├── fixtures/   toy fleet for tests/demo     ├─ topology  (call-chain edges)
└── spring-fleet.config.example.json         ├─ traceKeys ["sessionId", ...]
   (fake sample values)                      └─ logDir
```

The plugin never hard-codes paths, ports, or service names. Everything specific
is read from the user's config at runtime.

## Config manifest — `spring-fleet.config.json`

Generated by `/fleet-init`, editable by hand. Shape:

```json
{
  "reposRoot": "C:/repositories/backend",
  "buildTool": { "type": "gradle", "module": "-p {module}", "run": "bootRun", "test": "test" },
  "logDir": "C:/repositories/.spring-fleet-logs",
  "traceKeys": ["sessionId"],
  "proxyLib": "wg-api-proxy-lib",
  "sharedLibs": [
    { "name": "lts-core-cloud", "path": "lts-core-cloud",
      "modules": ["entities", "data", "orderflow", "external", "ws-caller", "gds", "util"] }
  ],
  "services": [
    { "name": "ordermanager", "path": "wg-ordermanager-api", "port": 8080,
      "contextPath": "/wg-ordermanager-v1", "logFile": "ordermanager.log", "role": "orchestrator" }
  ],
  "topology": {
    "entry": ["ordermanager"],
    "edges": [["ordermanager","search"],["ordermanager","ancillary"],
              ["ordermanager","booking"],["ordermanager","payment"],
              ["ordermanager","email"],["ordermanager","invoice"]]
  }
}
```

A `spring-fleet.config.example.json` with a **fake** toy fleet (`order-api`,
`payment-api`, `core-lib`) ships in the repo. The real config is `.gitignore`d.

### `/fleet-init` discovery
Scans `reposRoot`; for each repo reads `build.gradle`/`pom.xml` (build tool,
module name) and `application.properties`/`application.yml` (server port,
context path) and any logback config (existing MDC keys). Produces a draft
config and asks the user to confirm topology + trace keys (the only parts not
mechanically inferable).

## Commands

| Command | Pillar | Behavior |
|---|---|---|
| `/fleet-init` | setup | Scan repos → generate/update `spring-fleet.config.json` |
| `/trace <endpoint\|feature>` | A | Map the call chain across repos + shared libs, cite `file:line`, follow proxy-lib hops, in topology order |
| `/debug <sessionId \| error snippet>` | B ⭐ | Correlate logs across services by trace key → unified timeline → locate failure → map to source → cause + suggested fix |
| `/logs <service\|all> [--grep --since --follow]` | B | Tail/aggregate logs from `logDir` |

Deferred: `/run` (launch + tee), `/impact` (shared-lib consumers).

## Agents

- **`fleet-explorer`** — topology-aware multi-repo code explorer. Knows it spans
  N repos + shared libs; follows proxy-lib client calls across repo boundaries.
  Powers `/trace`. Returns structured call-chain with citations.
- **`log-correlator`** — reads many service logs, filters by trace key, builds one
  chronological cross-service timeline, isolates the error. Powers `/debug`.

Both run as context-isolated subagents so large multi-repo searches don't flood
the main context.

## Logging strategy (makes B reliable despite "logs vary")

The plugin guarantees a stable log location, per-service, two ways:

1. **Logback convention (opt-in, preferred):** a drop-in `logback-spring.xml`
   snippet that writes `${logDir}/<service>.log` with `%X{sessionId}` (+ other
   configured trace keys) in the pattern, with a rolling policy. Idempotent
   install; the `spring-fleet-logging-setup` skill walks through adding it.
2. **Run-and-tee (deferred `/run`):** launch services and tee stdout to the same
   `logDir` — for services the user won't modify.

If no trace key is present in logs, `/debug` falls back to timestamp + endpoint
correlation and says so explicitly.

## Skills (the know-how)

- `tracing-across-services` — how to map a call chain across repos using topology
  + proxy lib; how to cite and present the chain.
- `debugging-runtime-logs` — how to correlate by trace key, build a timeline,
  isolate the failing hop, map a stack trace back to source.
- `spring-fleet-logging-setup` — how to install the logback convention idempotently.

## Data flow

**`/debug <sessionId>`**
1. Read config → services, logDir, traceKeys.
2. `log-correlator` greps `${logDir}/*.log` for the sessionId → lines tagged with
   service + timestamp.
3. Build unified chronological timeline across services.
4. Find the exception/error → originating service + stack.
5. `fleet-explorer` maps the stack/endpoint back to source (`file:line`).
6. Synthesize: what happened, where it broke, likely cause, suggested fix.

**`/trace <endpoint|feature>`**
1. Read config topology.
2. `fleet-explorer` finds the entry controller, follows service calls (direct +
   via proxy lib) across repos.
3. Output: ordered call chain with `file:line` cites + which shared-lib code each
   hop touches.

## Error handling

- Missing/invalid config → prompt to run `/fleet-init`.
- No logs found for a service → `/debug` reports it, suggests logging-setup.
- No trace key configured/present → fall back to timestamp+endpoint correlation.
- Repo path in config doesn't exist → warn, skip that service, continue.

## Privacy / generic guarantee

- Plugin code + docs use placeholders only (`order-api`, `core-lib`, `${logDir}`).
- `spring-fleet.config.json` is `.gitignore`d; example file uses fake values.
- README + CONTRIBUTING note: "never commit a real `spring-fleet.config.json`."
- No service names, ports, paths, or trace-key values appear anywhere in the repo.

## Testing

- Ship a tiny **fixture fleet** (2–3 fake services + fixture log files) under
  `fixtures/`.
- Unit-test scripts (repo scan, log tail/aggregate, trace-key correlation)
  against the fixtures.
- Validate each command end-to-end against the fixture fleet.

## Packaging (community-ready)

- `plugin.json` (or `.claude-plugin/plugin.json`) manifest + `marketplace.json`.
- Cross-platform scripts: `.ps1` and `.sh` variants, deterministic logic in
  scripts so commands/agents stay thin.
- Maven or Gradle via `buildTool` in config.
- MIT `LICENSE`, `README.md` (quickstart: install → `/fleet-init` → `/trace` /
  `/debug`), `CONTRIBUTING.md`, `.gitignore`.

## Scope

- **MVP (first plan):** config schema + `/fleet-init` + `/trace` + `/debug` +
  `spring-fleet-logging-setup` + `fleet-explorer` + `log-correlator` + scripts +
  fixtures + packaging. Delivers A+B end-to-end.
- **Later:** `/impact`, `/run` (launch+tee) + group orchestration, optional
  SessionStart fleet-awareness hook, marketplace publishing polish.
